## 2. What Was Tested & What Worked (Verified)

* **The route, chosen by the agent.** The request named the pano, view and height, and asked for a rebuild "from its Street View photo". The agent ran:
  1. `load_tools`;
  2. `streetview_grounding_image`: pano `2GCrQKIND0ZilG2zd2QY-Q`, heading 359.9, pitch +12.4 (down, the grounding API's sign), fov 24.4, saved as `build/streetview-grounding/2GCrQKIND0ZilG2zd2QY-Q_h360_p12_f24.jpg`;
  3. `build_3d_object_from_reference`, with that file as `referenceImageUrl`, target "the weathered beige concrete trash can", `heightHintMeters` 0.91 and `sizeSource` "registered Street View photos (0.91 m)".
  * No image model was called (the server log's chat turns, and the record has no `imageModel`).
* **The cut-out, live.**
  * gemini-4-argon boxed the bin.
  * The MediaPipe interactive segmenter with GrabCut cut it out (2.5 % of the photo) in 8.6 s.
  * It was laid on #808080 as a 351 px square, in memory (no new file under `build/` or `public/` holds it).
  * The live viewer showed the cut-out while the spec was read.
* **The photo's viewpoint.** The spec read put the camera at azimuth 32°, elevation 14° from the bin's front.
  * The elevation agrees with the photo's 12.4° downward pitch.
  * The render from there (sheet panel 3) shows what the photo shows: the ochre panelled face on the left, the plain side on the right.
* **The size is held.**
  * Pass 1 came out 1.157 m tall. The check sent back "The build is 1.157 m tall but the object is 0.91 m tall (registered Street View photos (0.91 m)); scale every part so it stands 0.91 m tall."
  * Pass 2 stood at 0.91 m.
  * Result: 0.56 × 0.91 × 0.572 m, `size.label` `as-given`, its note naming the source.
* **Provenance in the record and the GLB.** `materials.label` is `photo-inferred`, and `back_panel` is `generated`.
  * The spec read named it as unseen, and the build's own view from the photo's viewpoint does not see it: the two agree.
  * GLB `materials[*].extras.scratchbox.provenance`:
    * `main_body`, `front_panel`, `top_opening_rim`: `photo-inferred`;
    * `back_panel`: `generated`.
  * `asset.extras.scratchbox` carries `sizeProvenance` and `photoReference`.
* **Time and cost.**
  * Build: 119 s over 3 passes (3 spec reads, 6 comparisons, native builds 2.6–3.3 s each). The whole chat turn took about 3 minutes.
  * Cost: under $1 by token count (spec reads 6–8k prompt tokens each, comparisons about 3.4k each, chat turns about 55k with cache hits). There is no billing readout.
* **The viewer's caption (run 2, after a fix).** The live overlay read "Internal reference · generated by an image model" over the photo's cut-out.
  * Fixed with `ObjectBuildLive.referenceCaption`.
  * After a server restart, a second build from the same photo showed "Cut out of a real photo · materials photo-inferred" (DOM text read from `.sb-object-build-live`).
* **Run 2, a repeat from the same photo.** The follow-up asked for the fluting across the whole panel and no detail pass. The agent called `build_3d_object_from_reference` directly with the saved grounding file.
  * 147 s, 3 passes. Built 0.54 × 0.92 × 0.555 m, height held at 0.91 m (as-given).
  * Photo view: azimuth 42°, elevation 12° (run 1: 32°, 14°).
  * Generated parts:
    * `front_panel`, the backing behind the new ribs: out of the photo's view of the build (the geometric test);
    * `top_opening_recess`: named hidden by the reader.
  * The other five parts are photo-inferred.
* **The agent's DETAIL PASS.** After run 1 the agent also ran `object_detail_pass` on its own (generated wear: edges, grime, streaks, dust) and said so in its reply. The sheet's panel 8 shows that version.

## 3. What Broke / Didn't Work

* **The front panel's fluting.** The reader built it as ribs along the panel's two edges with a flat middle; the photo shows ribs across the whole recess.
  * The comparison flagged it with high confidence on passes 2 and 3, and two revisions did not fix it.
  * It is reported in the result as a remaining difference.
* **Run 2's shape is worse than run 1's.** Four high-confidence differences remain after 3 passes:
  * the ribs are buried inside `core_body`, because the recessed panel sits behind the body's front face;
  * the frame bars stand proud of the body instead of flush.
  * The spec reader's recessed panels (a recess cut into a body) are the weak point in both runs. The size, the cut-out and the provenance held in both.
* **Per-part, not per-face, provenance.** A part the photo partly shows is labelled photo-inferred as a whole: the back of `main_body` is labelled with the body although the photo does not see it. A per-face (or per-texel) label would need the visibility test per triangle.
* **The live overlay's caption** said a photo's cut-out was drawn by an image model (fixed, section 2).
* **Viewer framing** (not this change): the chat's visual check scored 48/100 for "camera framing heavily offset". The viewport screenshot framed the object normally.

## 4. Candidate Tool/Service Ideas

* **`location_street_objects` → `build_3d_object_from_reference` fallback.** When the street-objects grammar keeps the scan's blob (silhouette no closer, e.g. benches and newsstands), hand its best clear view and the family's height to the photo route.
  * Today the agent has to be told the pano and view by hand, as in this run.
* **Per-face provenance for photo builds.** Run `partsSeenFrom`'s depth buffer per triangle and write a per-vertex label (or split a part's mesh at the visibility edge), so the unseen back of a seen part is labelled generated.
* **Detail pass read from the photo.** `object_detail_pass` invents wear from the object's kind and age. For a photo build, its decals and wear strengths could be read from the same photo, as photo-inferred.
