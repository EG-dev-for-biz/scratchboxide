## 3. What Broke / Didn't Work

* **Pipeline I's procedural/Trellis stage never runs** — requested explicitly (first by name, then via `isolate: true, pipeline: "i"`, then via `retryStage: "grammar"`) → the build falls back to the remesh/fit/detail pipeline every time, before the character-sheet + Trellis best-of-6 stage is ever reached.

  - Console evidence: none — this is a reported tool-level degradation, not a client error.
  - Suspected cause: the `remesh` stage's vector/scan roof-agreement gate (see `pipeline-e/enhance.ts` and the orchestrator's vector-massing check) uses a fixed max-deviation threshold (11.46 m here) unsuited to supertall buildings with large stepped setbacks/spires, where the Google vector massing's single roof height is a poor proxy for the real silhouette. This structurally blocks Pipeline I (`pipeline-i/`) for any building with this shape, not just the Empire State Building.

## 4. Candidate Tool/Service Ideas

* **Per-setback vector/scan agreement check** — instead of gating on a single roof-height deviation, compare the vector massing against the scan at each major setback tier (or use the scan's height histogram) before falling back. Would let Pipeline I's procedural base survive for stepped supertalls instead of unconditionally falling to pipeline E/H's remesh path.
* **Texture fit diagnostics surfaced earlier** — the texture pass failure ("does not fit in 2048x2048 texels even at 0.0008 texels/m") is a predictable consequence of the building's huge vertical extent vs. a single 2048 atlas; a pre-flight estimate (texel budget vs. structure surface area) before running the expensive remesh/survey chain would save ~3 minutes of wasted staging time on supertalls that are going to fail texturing anyway.

## 5d. Texture coverage follow-up (2026-10-24, same session): adaptive donor-search radius for rung-4 repeat fill

Asked how to get texture *coverage* for the entire building. The texture ladder (`TEXTURE_LADDER_RUNGS`) is already plane-aware, not object-aware, by design (`texture-repeat.ts`'s `detectPlaneRepeats`/`repeatFill`): it gates a periodic pitch per UV-mapped plane with a real statistical test (lagged NCC ≥ `NCC_GATE`, phase amplitude ≥ `K_SIGMA` standard errors of noise, ≥ `MIN_REPEATS` independent repeats) over real (rung 0–2) texels only, then fills gaps by averaging real donor texels at the matching phase — never by recognising "this looks like a repetitive skyscraper." That's the right shape of logic per this repo's own ADA rules (AGENTS.md §1.2: never branch on what kind of thing something is).

The one real limit found: `DONOR_SEARCH_PERIODS = 8` was a **flat constant** — donors were searched at most 8 pitch-periods away, regardless of how far apart a plane's actual real-evidence clusters are. For a supertall with denser Street View/tile-photo coverage near the base and sparser coverage toward the crown, any gap between real-evidence bands wider than 8 periods left those texels with too few donors, falling straight through to the flat palette rung even though the pitch itself was validated for the whole plane — the same "constant tuned for an ordinary building" pattern as every other fix this session (`HELD_OUT_STRIPES`/`BANDS`, the old texture-atlas `maxSide`, the old 4-face survey).

**Fixed**: `findDonors()` (`texture-repeat.ts`) now starts at `DONOR_SEARCH_PERIODS` (fast path, unchanged for the common case) and doubles the search radius up to a new `MAX_DONOR_SEARCH_PERIODS = 64` until `MIN_DONORS` are found or the ceiling is reached, instead of giving up at a fixed radius. `repeatFill`'s inline donor-search block now calls this helper. `TEXTURE_PASS_VERSION` bumped (`/16` → `/17`).

Tests: new case in `packages/core/test/texture-repeat-inference.test.ts` — a 1000-row synthetic plane with real evidence only in two dense bands at top and bottom and an 801-row (80 m) gap between them; a mid-gap texel 40 m from the nearest real band (beyond the old 8 m search, within the new 64 m ceiling) gets correctly filled. Verified this test actually exercises the fix: it fails (`MAX_DONOR_SEARCH_PERIODS` undefined) with `texture-repeat.ts` stashed back to its pre-fix state. `tsc --noEmit` clean; 34/34 across the six touched test files (`texture-repeat-inference`, `facade-texture-quality`, `pipeline-e-face-texture-repeat`, `staged-texture-pass-ladder`, `staged-texture-worker`, `palette-fill-height-band`) plus the new case, all passing.

## 8. Root cause of the 16% footprint coverage (2026-10-25, traced by a peer session, verified here)

A separate session ("Massing capability review," working on the unrelated outward-over-extension bug in pipeline E's vector massing) traced *this* doc's open §7 caveat while investigating a different problem, and sent the finding over. Verified directly against the code before recording it here:

* **`registerToFootprint`** (`pipeline-i/register.ts:90`) locks scale to height on the first line of real work: `const s0 = target.heightM / h;` — then only ever refines within `f` in `[0.9, 1.1001]` step `0.025` (line ~115) around that single height-derived scale, applied **isotropically** (`diag(m*s, s, s)` in the final matrix — one scalar `s` for all three axes, confirmed at the `matrix = [...]` line). There is no independent search over plan (x/z) scale at all, ever — only ±10% around whatever height-locked `s0` was computed.
* **Mechanism**: if Trellis's own reconstruction has a footprint-to-height aspect ratio that doesn't match the real building — very plausible for a 443 m supertall, where the four-view character sheet necessarily foreshortens/crops the plan at that scale — the registration comes out correctly scaled in height (by construction, `s0` forces that) but badly undersized in plan, and never trips the overflow check because the scaling is uniform: nothing pokes outside the footprint, it just doesn't fill it. Exactly "0% outside, 16% covered."
* **Why best-of-6 seed selection didn't catch it**: confirmed at `seed-score.ts:20,76` — `SILHOUETTE_WEIGHT = 0.7`, `score = 0.7 × meanSilhouetteIoU + 0.3 × planIoU`. Silhouette IoU is scored against the character sheet's *own* four camera views — a model can match its own generating sheet's silhouette from every angle while still having the wrong absolute footprint:height ratio in world space, since the sheet itself carries that same skew. All six seeds are generated from the same sheet with the same height-locked registration math, so they likely share the same systemic error — nothing in seed selection would surface it even in principle.
* **Not supertall-exclusive**: the underlying mechanism (isotropic, height-locked scale with only ±10% slack) can misregister any building where Trellis's reconstructed proportions drift from reality; it's just far more likely on a supertall, where extreme height drives more sheet foreshortening.
* **Not yet fixed** — the peer session traced the cause but did not design the fix. The shape of the fix is clear from the trace (give `registerToFootprint` an independent plan-scale search dimension instead of the uniform height-locked `s0 × f` search — e.g. search `sx`/`sz` scale independently of `sy`/height, or at minimum widen and decouple the plan-axis refinement from the ±10% isotropic band), but it hasn't been designed or attempted here. This is a strong candidate for the next increment, arguably ahead of the photo-match-judge fallback (§5b/§7) — a correctly-proportioned-but-unverified model is a smaller problem than a verification gate papering over a model that's structurally the wrong shape in plan.

**Recommendation sent to the peer session** (not implemented or tested here): decouple plan scale from height scale entirely rather than just widening the existing ±10% band.
1. Keep `sHeight = target.heightM / h` fixed (or a very narrow ±2-5% margin) — height is the one axis directly measured against the scan, worth trusting.
2. Derive the plan-scale search's starting point independently, from the model's own raw plan extent (bounding diameter of `px`/`pz` before scaling) vs. the target footprint's plan extent — not by borrowing `s0` from height at all, which removes the coupling at its source rather than just at the search range.
3. Search `sPlan` over a genuinely wide range around that plan-derived guess — the ESB case needed roughly a 2-3x correction to go from 16% to full coverage, well beyond any ±10% band, so a geometrically-stepped wide search is likely needed, not a linear one.
4. `place()` already only ever touches x/z, so it barely needs to change — the real change is the final world matrix: isotropic `diag(m·s, s, s)` → anisotropic `diag(m·sPlan, sHeight, sPlan)`.
5. Report the `sPlan`/`sHeight` ratio in `RegistrationFit`'s output — an extreme ratio is itself a useful signal (Trellis's reconstructed proportions may just be wrong, independent of registration quality), and a good input to whatever eventually implements the photo-match-judge fallback.
6. Ripple effect to flag for whoever implements this: `RegistrationFit.scale` is currently a single number, read as one value by at least `orchestrator.ts`'s describe string and its `heightRatio` calc. Anisotropic scale means deciding what that field means going forward (probably: keep `scale` = `sHeight`, add a new `planScale` field) — a small type/consumer surface change, not purely internal to `register.ts`.

## 9. Fix implemented and verified (2026-10-25, same session, `2e6c2fd2`)

Implemented a version of §8's recommendation in `registerToFootprint`: height stays fixed at `s0 = target.heightM / h` (never re-searched — it's the one axis trusted against the scan), and horizontal scale is now searched independently per yaw/mirror seed, first over a wide coarse set (`0.25x`-`3x` of `s0`) before the existing narrow local refinement (now ±15% around whatever the coarse pass found, not ±10% around `s0` itself). The final matrix went from isotropic `diag(m·s, s, s)` to anisotropic `diag(m·sh, sy, sh)`.

Divergence from §8's exact field proposal: kept `RegistrationFit.scale` as the *horizontal* scale (it's what orchestrator.ts's log string actually describes — "how big did we make the footprint"), and `heightRatio` now reports the height fit, which is ~1.0 by construction since height is no longer re-searched. No new field added; this was simpler and all three existing consumers (`pipeline-i.ts`'s log line, and the two test files) read cleanly either way.

## 10. Live rerun result (2026-10-25, same session): fix works, but the real gap is shape, not scale

Ran a fresh end-to-end rebuild (`scratchbox-main-esb-demo`, retryStage: "grammar", a brand-new best-of-6 Trellis generation — not the cached one from §7): **plan IoU 0.16 → 0.19, footprint coverage 16% → 19%, overflow 0% → 2%.** Confirmed directly against the running app's Three.js scene (only the Pipeline I/J generated mesh — 2,933 vertices / 3,510 triangles, matching `stg-759c10bc-l2i~tex` — is actually instantiated in the viewport; the remesh/tiles/vector layers are not rendered once Pipeline I/J commits, so what's pictured below *is* the fitted generated model, not the measured scan standing in for it). A top-down shot confirms it directly: a compact, roughly-boxy footprint, visibly smaller than the real stepped/wedding-cake base.

**Honest read:** the fix is real and moved the number in the right direction, but the gain (16%→19%) is far smaller than the unit test's synthetic case (where it went from 0.385 to >0.8) suggested it might. The reason: the synthetic test case was *pure scale error* (same shape, wrong size) — exactly what an independent scale search fixes. The real Trellis output's problem is evidently shape, not just scale: a 3,510-triangle mesh is far too simple to carry the real ESB's stepped setbacks and wide base, so even at its IoU-optimal scale, a correctly-proportioned-everywhere-else slender tower can't cover a footprint whose real shape it never had. Register.ts's scale search is working as designed (confirmed by the drop in overflow staying near 0%, meaning it isn't guessing too big) — it's finding the best scale for the shape it has, and that shape's ceiling is low.

**What this changes going forward:** the register.ts fix should stay (it's a genuine, verified improvement and a correctness fix regardless), but it is not sufficient on its own for supertalls with complex massing. The next lever is upstream of registration — either the character sheet needs to better convey the base/setback geometry to Trellis (more/better-chosen stations, explicit setback callouts), or this is a case for `pipeline-i/refine.ts`'s facade-projection approach once it can run without pipeline E's massing (§9's still-open item from the "Intelligent bounding box system" session's reply) — projecting real wall evidence onto the generated model doesn't fix its plan shape, but a geometry-aware massing fallback (scan-derived footprint prisms, not Trellis, as the *base* for a stepped supertall) might be a more promising direction than iterating further on `register.ts` alone.
