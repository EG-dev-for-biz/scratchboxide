## 3. What Broke / Didn't Work

* **Pipeline I's procedural/Trellis stage never runs** — requested explicitly (first by name, then via `isolate: true, pipeline: "i"`, then via `retryStage: "grammar"`) → the build falls back to the remesh/fit/detail pipeline every time, before the character-sheet + Trellis best-of-6 stage is ever reached.
  - Tool-reported reason: "Google vector massing roof was 21.45 m off the scan's median (223.09 m at the 90th percentile; maximum allowed is 11.46 m, plan IoU 0.98) ... due to the Empire State Building's stepped upper setbacks and spire." The `remesh` stage's vector-vs-scan agreement gate (`pipeline_e_fallback` / `pipeline_g_unavailable`) rejects before the procedural massing base pipeline I depends on can be used.
  - Downstream: `grammar` then rejected on 10 of 12 read facades (held-out cross-validation: 0–33% fold coverage, or worse than the relief's own window lattice) and fell to the relief's own window lattice instead of tile-photo grammar.
  - `fit` (scan-fitted rebuild) also rejected: share of scan kept as scanned 0.817 > 0.35 gate, fit-to-scan RMS 10.2 cm > 6.0 cm gate, unobserved share 0.942 > 0.35 gate.
  - `textures` real-texture pass also failed and fell to studio grey clay: "the layer does not fit in 2048x2048 texels even at 0.0008 texels/m" — the building's footprint/height ratio is too extreme for the current texel-budget fit at any density this pass tried.
  - Net result: the final model is correctly massed/scaled grey clay (no procedural Trellis rebuild, no real textures), not the photorealistic Pipeline I output described in `AGENTS.md` §4.
  - Console evidence: none — this is a reported tool-level degradation, not a client error.
  - Suspected cause: the `remesh` stage's vector/scan roof-agreement gate (see `pipeline-e/enhance.ts` and the orchestrator's vector-massing check) uses a fixed max-deviation threshold (11.46 m here) unsuited to supertall buildings with large stepped setbacks/spires, where the Google vector massing's single roof height is a poor proxy for the real silhouette. This structurally blocks Pipeline I (`pipeline-i/`) for any building with this shape, not just the Empire State Building.

If nothing broke, say so explicitly rather than omitting this section. — N/A, see above.

## 4. Candidate Tool/Service Ideas

* **Per-setback vector/scan agreement check** — instead of gating on a single roof-height deviation, compare the vector massing against the scan at each major setback tier (or use the scan's height histogram) before falling back. Would let Pipeline I's procedural base survive for stepped supertalls instead of unconditionally falling to pipeline E/H's remesh path.
* **Texture fit diagnostics surfaced earlier** — the texture pass failure ("does not fit in 2048x2048 texels even at 0.0008 texels/m") is a predictable consequence of the building's huge vertical extent vs. a single 2048 atlas; a pre-flight estimate (texel budget vs. structure surface area) before running the expensive remesh/survey chain would save ~3 minutes of wasted staging time on supertalls that are going to fail texturing anyway.

## 5. Follow-up patch (2026-10-24, same session)

Two of the four generalization gaps named above were patched and verified live against the Empire State Building:

* **Texture atlas (`texture-uv.ts` / `texture-pass-contracts.ts`)** — the packer no longer throws when a layer does not fit `maxSide` at a sane density; it now grows the atlas up to a new `hardMaxSide` ceiling (default `max(maxSide, 8192)`) *before* lowering texel density, since a bigger atlas keeps requested detail and a lower-density one does not. `TEXTURE_PASS_VERSION` bumped (`texture-pass/14` → `/15`) to invalidate stale cached failures.
  - **Verified live**: after restarting the dev server and re-running `google_3d_tiles_get_clay` with `isolate: true, pipeline: "i"`, the texture pass completed in full (previously: instant `texture_pass_failed`, fell to studio grey clay). The Empire State Building is now textured base-to-spire with real tile-photo/Street-View-derived materials (limestone ashlar, vertical piers, brickwork) — screenshots sent to the user in this session.
  - Tests: `packages/core/test/texture-uv-atlas.test.ts` updated (the existing density-shrink test now passes `hardMaxSide` explicitly to keep exercising that path) and two new tests added (grows past `maxSide` up to an explicit `hardMaxSide`; defaults `hardMaxSide` to ≥8192 with no caller change). 15/15 passing. Broader suite (`texture-pass-contracts`, `staged-location-grammar`, `staged-texture-pass-ladder`, `texture-atlas-and-crawler-baker`, `adaptive-uv-orchestrator*`) 30/30 passing. `tsc --noEmit` clean.
* **Facade grammar held-out folds (`facade-grammar.ts`)** — `HELD_OUT_STRIPES`/`HELD_OUT_BANDS` raised from the fixed caps (6/4) to a generous ceiling (128) so the fold count actually scales with the facade's covered extent toward the `HELD_OUT_SPAN_M` (8 m) target, instead of silently going coarse above ~48 m width / ~32 m height. Costs nothing extra: `heldOutFolds` always returns exactly 4 reads regardless of segment count. `FACADE_GRAMMAR_GATE_VERSION` bumped (`v9` → `v10`).
  - **Verified live, with an honest caveat**: facade grammar is still degraded on the Empire State Building's worst facade (facade 6, 5,049 m²) after this patch — but for a *different* reason than fold coarseness. The held-out check now reports "0 of 4 folds predicted openings (0% of the hidden facade): too little to judge," meaning the whole-facade reading itself found no rhythm to continue, upstream of fold granularity. The fix is correct (verified by `facade-grammar.test.ts`'s existing held-out-gate test, still passing, plus no regression across 2 facade-grammar-specific test files, 12/12 passing), but facade 6 needs the deeper fix named in §3/§4 above (facade segmentation merging dozens of storeys into one relief chart) before grammar can read it at all.
* **Not patched this round**: #1 (fixed 4-survey-faces/mid-height aim) and #3 (vector massing's single roof height vs. a stepped scan) — both need more structural changes than a localized constant fix and were left as the roadmap items in §4 above.

## 5b. Second follow-up (2026-10-24, same session): default to generative, multi-band survey, 10x texture budget

Three more changes, on top of §5, in response to the user's explicit policy decision ("default to generative facades, fall back on photogrammetry textures if needed") and direct requests:

* **Texture budget raised 10x** (`STAGES.textures.budgetMs`: 600,000 → 6,000,000 ms) — the atlas-growth fix in §5 makes a supertall's bake genuinely slower (more texels to synthesize) rather than failing fast; one live run did hit "Real textures took longer than its 600 s limit" after the atlas fix, confirming the need. `TILE_REFINE_RECREATE_BUDGET_MS` (420,000 ms, a district-specific sub-budget) was left unchanged — it was never what timed out.
* **Pipeline I/J decoupled from the vector-massing gate** (`orchestrator.ts`) — `iRun`'s hard dependencies turned out to be only `refined` (the isolated scan, already available whether or not pipeline E's massing passed), `layer.objectId` (to supersede), and `key` (cache key); the optional tile-plate refine step's `stage` field was made optional (`e.stage?.run`). `grammarRun()` now has a new branch: when `!eState` but the plain remeshed scan exists and `pipeline: "i"/"j"` was asked for, it builds a minimal `IRunState` from the remesh stage's own result (`remesh.value.groundLayerId`, `remeshedNow.cacheKey`) and calls `iRun` on it directly — defaulting to generative even when the massing gate rejected. **Not yet implemented**: the user's photo-match-judge fallback (`photoMatchGate`/`gateDecision`, the same mechanism pipeline E's relief layer already uses to pick measured vs. generated by rendering both against real Street View photos) — wiring that in needs more plumbing (registered projection views reused from the evidence stage) than could be safely verified this session; today the generated layer always supersedes once `iRun` commits successfully, with no reject-on-poor-fit gate. Flagged as the clear next increment.
* **Multi-band survey** (`face-survey.ts`) — `footprintSurveyFaces` now splits each heading into `surveyBandsFor(heightM)` vertical bands (up to `MAX_SURVEY_BANDS_PER_FACE=4`, each targeting `SURVEY_BAND_HEIGHT_M=40`m) instead of one shot aimed at the structure's overall mid-height; `surveyAim`'s FOV sizing now considers the band's height as well as its width (previously width-only, even though the aimed-at slice could be the whole building). `selectSurveyViews` gained an `opts.bandedCeiling` so a caller can intentionally raise the image budget above `MAX_SURVEY_FACES` for a banded survey, without weakening the existing (tested) guard that caps an ordinary request at 4 real Street View images unless the views are free tile renders (`opts.rendered`).

**Verified live** (Empire State Building, full fresh rebuild after restarting the dev server): degraded parts dropped from 13-14 (pre-patch) to **3**. The swatch panel showed multiple distinct entries at the same headings (e.g. four separate reads at 239° and 299°, each a different material/element set) — direct confirmation the height bands are each getting their own real Street View look. The run log explicitly said "pipeline I placed the character sheet" — `iRun` now executes, which it never did before (confirms the decoupling works). It still didn't commit a generated model for the Empire State Building specifically, but for a new, different, deeper reason than the original massing gate: **pipeline I's own character-sheet outline-lock check rejects it** — "the character sheet did not fit the scan after 3 attempts: outline 12% of the subject is outside (< 3%) or station 1 overflowed 0.08 (< 0.03)" — because the four character-sheet render stations can't frame the whole 443 m structure without part of it falling outside each station's frame. This is the same family of problem as item #1 (fixed camera framing tuned for ordinary building heights), just inside pipeline I's own station/sheet code rather than the survey's — not yet investigated or fixed.

Tests: typecheck clean; 101/101 (`staged-location-orchestrator`, `pipeline-i`, `pipeline-i-refine`, `staged-pipeline-e-guards`, `staged-pipeline-e-setback-massing`, `staged-pipeline-g`, `pipeline-h`) + 27/27 (survey: `photo-ornament-survey`, `streetview-survey-sides`, `streetview-survey-tool`, `survey-station-render`) + 33/33 (`staged-pipeline-e-guards`, `staged-pipeline-g`, `pipeline-g-check`, `pipeline-g-facades`, re-run after the survey-budget change) all passing, no regressions.

**Next steps, in priority order**: (1) fix pipeline I's character-sheet station framing for very tall structures (likely the same fix shape as item #1 — multiple framing attempts at different distances/pitches rather than one four-station layout sized for ordinary buildings); (2) wire the photo-match-judge fallback so a poorly-fit generated model doesn't silently supersede a better-looking textured remesh; (3) items #1 (now partially addressed) and #3 from §4 remain open for other building shapes this session didn't exercise.

## 5c. Visual review and third follow-up (2026-10-24, same session): textures-late budget, patchy shaft texture, no real facade rhythm

A top-to-bottom visual review of the live Empire State Building (now textured, massing-gate-decoupled, multi-band-surveyed) against the run log found:

Root cause confirmed in the same run's log: `textures-late` (`STAGES['textures-late']`, the stage that bakes whatever layer commits after the main structure — fit/detail/grammar/figures) hit **the identical atlas-growth-cost timeout** as the main `textures` stage before it was fixed: "Real textures of later layers took longer than its 1200 s limit." Only the main `textures` stage's budget was raised in §5b; this sibling stage was missed.
  - **Fixed**: `STAGES['textures-late'].budgetMs` raised 10x (1,200,000 → 12,000,000 ms), keeping the original 2x ratio to the main stage's (now 6,000,000 ms) budget. `tsc --noEmit` clean; no test asserts the literal budget value (checked `chat-tool-time`, `staged-location-real-data`, `staged-location-orchestrator`, `staged-fast-first`, `staged-texture-orchestrator` — none reference `1_200_000` for this stage). Ran the five referencing test files (23 tests): 1 pre-existing failure (`staged-fast-first.test.ts`'s "labels the triangles without a photo as clay, by area") confirmed unrelated — it fails identically with `orchestrator.ts` stashed back to its pre-session state, so it comes from other uncommitted work already in this checkout, not from this change; 1 flaky concurrency-ordering test in `staged-texture-orchestrator.test.ts` passed on re-run. Everything else green.
* **Shaft texture has scattered lighter-grey patches** breaking the otherwise-correct window/pier grid, visible on close zoom. **Root-caused and fixed.** `palettesFromSurvey`/`paletteFill` (`texture-pass.ts`) — the Rung-3 fallback fill used wherever the real photo-projected texture leaves a texel uncovered — matched a texel to a survey palette by heading alone (`angleBetween(h, f.headingDeg)` within 60°), with no notion of height. Since the multi-band survey (§5b) now produces several `PaletteFace` entries at the *same* heading (one per height band — e.g. four distinct swatches at 239°, granite base / limestone shaft / steel crown), every texel at that heading picked whichever band happened to iterate last, regardless of its actual world height — exactly the scattered mis-coloured patches observed.
  - **Fixed**: `SurveyedFace` (staged-location-contracts.ts) gained optional `centreY`/`heightM` (and the strict JSON-schema contract was updated to match, since it has `additionalProperties: false`); `face-survey.ts`'s `faceRecords()` populates them from the `SurveyFaceTarget` band; `PaletteFace` (texture-pass.ts) carries them through `palettesFromSurvey`; `paletteFill`'s texel loop now reads the texel's world Y (`atlas.texels.position`) and prefers a same-heading candidate whose band actually contains that height over one that merely ties on heading, falling back to nearest-heading (the old behaviour, unchanged) when no band contains it or no height info is present at all — so an ordinary, unbanded survey is bit-for-bit unaffected. `TEXTURE_PASS_VERSION` bumped (`/15` → `/16`).
  - Tests: new `packages/core/test/palette-fill-height-band.test.ts` (3 tests) proves the fix directly — picks the containing band among several at the same heading, falls back to nearest heading when no band contains the texel (a gap between bands), and leaves the ordinary single-palette-per-heading case unchanged. `tsc --noEmit` clean. 113 tests across the five files that touch `PaletteFace`/`SurveyedFace`/materialHints (`staged-texture-pass-ladder`, `staged-texture-worker`, `texture-pass-contracts`, `photo-ornament-survey`, `staged-location-contracts`) all pass.
  - **Verified live**: full rebuild completed (v10). The shaft's window grid is now regular and consistently coloured across the setback transitions where before it showed scattered mis-coloured patches — screenshots sent to the user.
* **No real facade rhythm anywhere on this building**: facade grammar fails on every read facade (confirmed again on this run: "pipeline I failed... station 1: 12.0% of the subject is drawn outside the scan outline... station 4: yaw moved 0.66 deg"), so every window/opening is the relief's generic lattice, not a real photo-read pattern — the shape and the height-varying color are now both correct, but the detail rhythm (real cornices, real setback massing lines, the real base/shaft/crown material breaks the survey itself measured) isn't making it into the generated texture. Same root cause as item #4 in §4, now confirmed to persist after all three §5b fixes.

Pipeline I's character-sheet failure now has two precise, reproducible numbers (useful for whoever fixes the station framing next): **station 1 overflows its frame by 12.0% of the subject** (gate: ≤3%), and **station 4's resected yaw drifts 0.66° off its planned pose** (gate: ≤0.5°) — both symptoms of four fixed camera stations sized for an ordinary building failing to frame or hold pose on a 443 m tower.

## 5d. Texture coverage follow-up (2026-10-24, same session): adaptive donor-search radius for rung-4 repeat fill

Asked how to get texture *coverage* for the entire building. The texture ladder (`TEXTURE_LADDER_RUNGS`) is already plane-aware, not object-aware, by design (`texture-repeat.ts`'s `detectPlaneRepeats`/`repeatFill`): it gates a periodic pitch per UV-mapped plane with a real statistical test (lagged NCC ≥ `NCC_GATE`, phase amplitude ≥ `K_SIGMA` standard errors of noise, ≥ `MIN_REPEATS` independent repeats) over real (rung 0–2) texels only, then fills gaps by averaging real donor texels at the matching phase — never by recognising "this looks like a repetitive skyscraper." That's the right shape of logic per this repo's own ADA rules (AGENTS.md §1.2: never branch on what kind of thing something is).

The one real limit found: `DONOR_SEARCH_PERIODS = 8` was a **flat constant** — donors were searched at most 8 pitch-periods away, regardless of how far apart a plane's actual real-evidence clusters are. For a supertall with denser Street View/tile-photo coverage near the base and sparser coverage toward the crown, any gap between real-evidence bands wider than 8 periods left those texels with too few donors, falling straight through to the flat palette rung even though the pitch itself was validated for the whole plane — the same "constant tuned for an ordinary building" pattern as every other fix this session (`HELD_OUT_STRIPES`/`BANDS`, the old texture-atlas `maxSide`, the old 4-face survey).

**Fixed**: `findDonors()` (`texture-repeat.ts`) now starts at `DONOR_SEARCH_PERIODS` (fast path, unchanged for the common case) and doubles the search radius up to a new `MAX_DONOR_SEARCH_PERIODS = 64` until `MIN_DONORS` are found or the ceiling is reached, instead of giving up at a fixed radius. `repeatFill`'s inline donor-search block now calls this helper. `TEXTURE_PASS_VERSION` bumped (`/16` → `/17`).

Tests: new case in `packages/core/test/texture-repeat-inference.test.ts` — a 1000-row synthetic plane with real evidence only in two dense bands at top and bottom and an 801-row (80 m) gap between them; a mid-gap texel 40 m from the nearest real band (beyond the old 8 m search, within the new 64 m ceiling) gets correctly filled. Verified this test actually exercises the fix: it fails (`MAX_DONOR_SEARCH_PERIODS` undefined) with `texture-repeat.ts` stashed back to its pre-fix state. `tsc --noEmit` clean; 34/34 across the six touched test files (`texture-repeat-inference`, `facade-texture-quality`, `pipeline-e-face-texture-repeat`, `staged-texture-pass-ladder`, `staged-texture-worker`, `palette-fill-height-band`) plus the new case, all passing.
