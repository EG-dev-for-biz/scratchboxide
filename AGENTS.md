# Scratchbox IDE Agent Directives

These rules are for coding agents changing this repository. The in-app chat model never reads this file: what it must know lives in its system prompt (`packages/core/src/node/gemini/prompt-builder.ts`), its tool descriptions (`packages/core/src/node/gemini/tools/`) and its skills (`.agents/skills/`). Product behaviour that must always hold is enforced in code; this file names where. For any tool's parameters, read its declaration (the generated reference: `npm run docs:mcp`), not a copy here. `packages/core/test/instruction-tool-drift.test.ts` fails when this file, the system prompt, the capability resolver or a skill names a tool that does not exist.

## 1. Adaptive Domain Architecture (ADA): run this audit before planning or writing code

1. **The Alien Planet Test (zero closed taxonomies).** Ask: could an entity nobody anticipated ("a bioluminescent geothermal mycelium forest inside a hollow asteroid with liquid methane geysers") be represented without editing TypeScript or C++? If a new concept needs a new enum variant, union member or switch case, refactor into continuous parameters.
   - **No closed enums:** never `type Domain = 'arctic' | 'desert' | 'space' | 'urban'`.
   - **Open literals for labels only:** `type Topology = 'plateau' | 'canyon' | (string & {})`. Execution never branches on string matches; it reads continuous fields (`peakReliefMeters`, `sharpnessExponent`, `roughness`, `turbidity`, `albedo`).
   - **Open feature-type vocabulary (labels only):** features may carry Google Vector Feature Tiles-style type codes (`types: string[]`, general → specific; Google's `FEATURE_TYPE_*` codes pass through unchanged, ours use `SB_FEATURE_TYPE_*`, catalogued in `packages/core/src/common/spatial/sb-feature-types.ts`). The vocabulary is open: unknown codes are kept, the catch-all `SB_FEATURE_TYPE_OBJECT` is always valid, and codes a model proposes are logged for review, never added silently. Codes serve prompting, labels, filtering and export only and never select a geometry path: geometry comes only from measurements and the four operators below.
2. **No taxonomic regex dictionaries; the LLM is the domain engine.** Never route or gate tools on noun lists (`/aqueduct|colonnade|arch|castle/i`, `/snow|arctic/i`). Never withhold workspace, canvas or spatial tools on a keyword miss.
3. **Dimensions, not domains.** Types define coordinate spaces, physical quantities and hardware invariants (`Vec3`, `Bounds3D`, PBR attributes, glTF buffer layout), never semantic categories. Test every type: can an unforeseen concept use it unchanged; can two states be interpolated; does it constrain *how* (execution) rather than *what* (imagination)?
4. **Schema contracts, not presets.** Structural contracts (`Scene3DData`, `KanbanData`, `NodeGraphData`, ...), never canned content, sample cards, mandated section titles or `sceneType` presets that force a shape. Structured scene data (`customMeshes`, `cppGenerator`, `objects`, `geoAnchor`, `splat`, `customScript`, `timeline`, `features`) always takes precedence. Offline fallbacks use lightweight entity extraction (`extractPromptEntities`), not switch trees.
5. **The four universal geometric operators.** Any part or detail of any asset (vehicle, machine, alien probe) is built from:
   1. SE(3) curve sweeps of a profile along a carrier curve with scale, twist and modulation (limbs, hoses, struts, coils, truss members);
   2. harmonic solids of revolution: a radial profile r(z) with K radial lobes and helical twist (housings, nozzles, flutes, augers, fins, cogs);
   3. affine metric replicators at a continuous pitch along curves or surfaces (bolt circles, louvres, teeth, treads);
   4. isoparametric normal relief fields (shut lines, weld beads, knurling, grooves).

   Never design schemas or code around named tool or mechanism categories (`drill`, `claw`, `camera`, `sensor_pod`).
6. **No canned asset libraries.** No finished mesh catalogues (`chiller_01.glb`, `pine_tree_03.glb`). Assets are generated by parametric grammars: Archie (`scratchbox_architecture.hpp`, `scratchbox_sb_archi.hpp`; building blocks `Loft3D`, `PolygonTriangulator`, `BvhTree`), SB-Veggie (`scratchbox_sb_veggie.hpp`), the engine's noise (`scratchbox_engine.hpp`). **Exception:** surface material libraries (colour, normal, roughness, opacity, displacement maps) are allowed when entries are chosen by appearance and real-world scale and tinted to measured data, never keyed by a closed category list. The first is `assets/textures/trees/`.

## 2. What the app can and cannot do

- **Solve with the app's own capabilities**, formulated first as transformations on 3D data the app already has. Don't reach for external apps (Blender, external photogrammetry) because another agent did.
  - **3D:** the native C++20 engine (`scratchbox_engine.hpp`) and Google Photorealistic 3D Tiles.
  - **Video:** the timeline NLE, matchmove and lens tools.
  - **Masks:** open-vocabulary segmentation (`vfx_segment_subject`, `ObjectSegmenterService`; a described object that is not found is a typed `SegmentTargetNotFoundError`).
  - **Google models:** Gemini vision, Nano Banana / Imagen images, Vertex AI.
  - **Meshy** (user decision, 2026-10-25): Meshy 7.1 multi-image-to-3D on Fal.ai, pipeline J's default model service. Its output is `generated`.
  - **Trellis** (user decision, 2026-10-24): Trellis multi on Fal.ai (pipeline J's Trellis model service, formerly pipeline I, the turnaround path), and the self-hosted Trellis services on Google Cloud (`scoutscan`): `trellis1-multi`, `trellis2-generate`, `trellis2-retexture` and `trellis2-lora-train`, behind one job gateway whose inputs and outputs are `gs://` objects and `job://<id>/<file>` references, so one service's output feeds another (`docs/research/2026-10-24-trellis-self-hosted-services-plan.md`). Their output is `generated`. The gateway is `SCRATCHBOX_TRELLIS_SERVICE_URL`; until it is deployed and set, the self-hosted services are unavailable, and the app says so.
  - **GPU tier:** inference runs on Cloud Run GPU (scale to zero), training on Vertex AI custom jobs; both are in project `scoutscan`.
- **Monocular depth:** supported on exactly one model, Depth Anything V2 Small (`PanoramaDepthService`, `tools/depth/panorama_depth.py`; weights in the gitignored `.model-cache/`). Scene depth and geometry come only from this model, the scan or the tiles, never from a brightness heuristic. Surface relief (normal and height maps within a few centimetres of a measured surface) may be inferred from the photo by a learned material model (e.g. CHORD, PATINA); it is labelled `photo-inferred` or `generated` and never moves the measured surface.
- **Unsupported:**
  - neural image-to-3D other than Meshy 7.1 and Trellis on their Fal.ai paths and the self-hosted Trellis services (e.g. TripoSR);
  - video-to-video restyling (AnimateDiff);
  - other depth models (Marigold);
  - custom LoRA checkpoints, except TRELLIS.2 adapters trained by `trellis2-lora-train`.

  Say so plainly. Never approximate, simulate a result or emit placeholder geometry. There is no ComfyUI tier; the only self-hosted GPU work is the Trellis services above.
- **`resolveTaskCapability`** (`packages/core/src/node/agent/task-capability-resolver.ts`) runs before each agent turn. It picks tool packs and reports `canSolveNatively: false` with a reason for unsupported tasks.
- **Runtime failures:** if native generation fails (e.g. a Clang error), surface the error. Never paper over it with another engine or client-side primitives.

## 3. 3D engine rules

1. **C++20 generates geometry; Three.js only renders.** Geometry comes from the native engine, compiled with `process.env.CXX || 'clang++'` `-std=c++20 -O3` through `NativeCppCompilerService` / `compileNativeCached`, and streamed as binary glTF (`.glb`). `-march=native` only behind `SCRATCHBOX_NATIVE_ARCH=1` (avoids SIGILL across machines). Three.js handles rendering, camera, post-processing and gizmos.
2. **No JavaScript generative primitives.** Never catch a backend failure and substitute `THREE.BoxGeometry` / `CylinderGeometry` / `ConeGeometry` / `SphereGeometry` stand-ins. `npm run lint:primitives` (`scripts/lint_no_js_primitives.js`) fails CI on them.
3. **Complexity floor.** Generated scenes must pass `GeometricComplexityGate` (25,000 vertices for scenes, 5,000 for single props, with a primary / secondary / tertiary 70-20-10 hierarchy), or be rejected with `GeometricFidelityViolationError`. **Measured geometry is exempt:** remeshed tiles and scan-fitted rebuilds are judged by their fit to the scan (coverage, RMS residual); never pad them.
4. **Ephemeral compilation, zero code proliferation.** No one-off scene `.cpp` files committed to `scripts/` or `src/` (`arctic_outpost.cpp`). Procedural C++ is synthesized from contracts, compiled ephemerally, and its source kept in scene data (`data.cppGenerator.sourceCode`, `glbPath`). Small reusable CLI drivers for engine headers (e.g. `scripts/staged_massing.cpp`) are fine.
5. **Forward mapping, never inverse fictions.** When the 3D ground truth exists (hair curves, geometry, camera matrices), project it directly into target buffers (`.spz`, `.ply`, `.glb`). Never round-trip through synthetic renders and neural 3DGS training (COLMAP / splatfacto) to re-estimate it.
   - **Grooms:** `scratchbox_hair.hpp` → `scratchbox_spz.hpp` (`AnalyticalGroomSplatService`).
   - **Groom shapes:** continuous surface descriptors, never shape enums.
6. **Zero uninvited defaults.** Never inject skyboxes, atmosphere domes, clouds, fog or cloud shadows. Unconfigured scenes are a neutral studio (`skybox: 'studio'`, `lighting: 'studio'`). Atmosphere, ephemeris, fog and clouds appear only when the prompt or contract asks for them. The viewport's Weather tool and the scene graph's Weather node are such a request: time of day, date, cloud cover, haze and fog go through one function (`scene-weather.ts` `applySceneWeather`; the sun from the ephemeris at the scene's place, else a plain sun path, never an assumed location), and "Off" restores the scene's prior sky. God rays are not an atmosphere opt-in: asking for them places a light emitter the rays stream from. **Real places are the one exception** (user decision, 2026-11-02):
   - **What:** a staged place (3D Building and 3D Scene: `composeStagedArtifact`) and a splat world (3D World: `SurveySplatPipelineService`, plus the starter, for worlds saved before) open under the place's own sky.
   - **The sky:** partly cloudy with a low afternoon sun, from the ephemeris at the place on the build's day (`scene-weather.ts` `withLocationSceneWeather`, `LOCATION_SCENE_WEATHER`: sun 20° up, cloud cover 0.4).
   - **Off:** the Weather tool's Off returns to the studio underneath, and stays off (`weatherCleared`).
   - **Staged into an open scene:** that scene keeps its own sky.
7. **Scene state stays in sync.** The scene JSON (`Scene3DData`), its C++ generator and the live viewport are three views of one scene. `Scene3DWorldLens` projects between them; an edit to one must reach the others.
8. **Modular packs.**
   - **Tools:** in-app Gemini tools live in domain packs under `packages/core/src/node/gemini/tools/`. `tool-registry.ts` only orchestrates; never add declarations or handlers there.
   - **Viewport operators:** they live in `packages/core/src/browser/generative-canvas/services/operators/`; `direct-dispatch-operator-engine.ts` only routes.

## 4. Product behaviour (enforced in code; keep the code and this summary in step)

- **3D/VFX product gate** (temporary, while the app is developed as a 3D and VFX tool; user ask, 2026-10-30). `SCRATCHBOX_PRODUCT_SCOPE=3d-vfx` in the environment the app starts with (server and Vite both read the process environment; unset, nothing changes) limits what can be made to 3D scenes and video timelines; node graphs and browser pages still show as companions the app opens. One module decides, by canvas type only (`common/product-scope.ts`):
  - **model:** the creating prompts describe only those types and put pictures in the chat (`scopedPersona`); `mount_canvas_primitive` and `morph_canvas_primitive` refuse other types with the reason; a tag of another type in a reply is not opened and the chat says why (`streaming.ts` `inScopeArtifact`); deep write answers 403;
  - **UI:** starter buttons, Spotlight, the sidebar "+" menu, the canvas "+" tab, View As, preview-in-canvas, the canvases' own morph buttons (the timeline's React Player, the browser's Morph to Code Sandbox, an image card's Insert into Code), file open and Admin demos offer nothing else, and the home headline, composer placeholder and sidebar "+" title name only 3D and video; off-scope slash commands and every gate refusal answer with a chat note (`chat/scopeNote.ts`; toasts are not shown);
  - **saved work:** never filtered from the chat store; a session's other canvases are hidden from tabs and stage and its out-of-scope mode shows as chat, and all of it returns when the gate is off.

- **Textured by default, clay on request** (user decision, 2026-10-19).
  - **The default:** new scenes open with their authored materials (`renderMode: 'pbr'`; the viewport default, `applyFirstPassBaseline` in `scene3d-first-pass-baseline.ts`).
  - **Clay** (`renderMode: 'clay'`, `sb.PbrMaterial.clay()`) is used:
    - when the user asks for it; the choice persists through `keepOpenSceneRenderMode` and `stagedBuild.materialMode`;
    - at a staged location while its textures are not yet ready (clay first, then an automatic crossfade to the textured twin);
    - for ground-truth and conditioning outputs: the clay blockout runner, `_clay` tile tools called for massing, survey clay renders, the location evidence tools, and shape review.
  - **Object builds** carry per-part material factors read from a generated reference (labelled `generated`).
- **Locations.** A real place named in the request is staged at that place from Google 3D Tiles. Never build synthetic ground slabs, fake terrain or procedural lollipop trees in a void instead. It opens under the place's partly cloudy, low-sun sky (§3.6). With no place named, the hero stands in a studio void. External neural 3D only when the user names it, or through pipeline I below.
- **Buildings win over trees** (user decision, 2026-10-21). Building facades and structure take precedence over vegetation in occupying space; never decimate a building for a tree. The tree strip (`scratchbox_tile_vegetation.hpp`) stops its cut at any wall, roof or building surface and keeps it whole; a wall a tree hid is continued as wall (labelled), never replaced by a cap or skirt; when tree and building cannot be told apart, the surface stays building. A planted crown never occupies building volume: it is clipped or the tree moved or shrunk outward, never the building cut or hidden. The surrounding terrain leaves a clear gap (`TERRAIN_HERO_GAP_M`) around the ground the tiles occupy, so two ground surfaces never share a patch.
- **Believability first, honestly labelled** (user decision, 2026-10-21; supersedes the narrower "realism first" line below and the old blanket "no fallbacks" refusal default — applies app-wide, not only to location builds).
  - **The goal everywhere the app shows content** is that it reads as believable, not that every value traces to a measurement. Where real data is missing, ambiguous, or a step can't get a clean answer, the default is a plausible, labelled fill (a sensible estimate, a generated detail, a fitted guess), not a refusal, a blank gap, a flat/clay fallback, or an "unsure" dead end left sitting in the build. A footprint with no measured height gets a plausible one instead of not being drawn; a scan cluster the residual audit can't classify gets a believable fit attempted instead of sitting as unexplained scan residue; a facade gap gets filled from whatever reading applies (a repeat, a sibling, a plausible generated detail) rather than staying blank or clay.
  - **Real data still leads.** Measured and vector-modelled data set what's known (massing, outline, dimensions, window rhythm, materials, colour, distinctive features); estimated and generated content fills what isn't. Content that erases or contradicts a labelled real or distinctive feature is still rejected or reverted in that region — believability means filling gaps convincingly, not overwriting what's known.
  - **Location builds specifically:** the goal is photorealism that stays recognisably the real place, not the closest copy of the data (the 2026-10-19 directive this one broadens). Generated and estimated detail is the default for finer detail and for surfaces no source covers, and is accepted when it raises the photo-match judge's realism without lowering identity.
  - **Believable within the designated footprint** (user decision, 2026-10-23). Scope: only the staged-location building rebuilds that convert Google Maps data (3D Tiles, vector tiles) into a building, i.e. pipeline E (and G, retired as a choice on 2026-10-30) and their massing/texture stages. It does not apply to the rest of the 3D system (object builds, scripted sculpts, districts as a whole). The target is the most believable version of the building that fits inside its designated footprint: the Google vector footprint, else the scan-derived outline (`scanDerivedFootprint`), else one the user gives. Inside that footprint and its height envelope (measured, else estimated), believability decides: geometry, relief, openings, ornament and full PBR materials (de-lit albedo, normal/height, roughness, metalness, AO) may be inferred, fitted or generated to read as the real building. Outside it nothing is added: no geometry, roof object, ornament or texture past the footprint or above the height envelope, except features the data itself shows rising above it (a spire, a mast). Real data still sets the footprint, height, massing and distinctive features; fill and detail serve likeness and never override them, and every part and texture channel keeps its provenance label.
  - **Provenance labels, always honest, and mandatory everywhere this applies.** Every part of a build is labelled `measured`, `vector-modelled`, `photo-inferred` or `generated` (the last now covers any plausible estimate or fill, procedural or image-model, not only drawn content), with a confidence, in GLB extras, tool results and the viewport's provenance view. A real-data-only view (opt-in) still shows only real sources, for anyone who wants it.
  - **Never** call generated or estimated content measured. **Never** claim a step ran when it did not. A filled gap always carries its real reason (no clean measurement, low confidence, a refused source) alongside the fill — the guess is honest about being a guess, it just isn't refused.
  - **Still real-data only, no filling:** tools whose entire output is handed elsewhere as a measurement, where a believable guess would make the deliverable wrong rather than the app more believable — footage and sun matching, physical measurement, AR alignment, and the location evidence tools called directly for ground truth (`location_building_shape`, `location_isolate_structure`, `location_split_block`, `location_residual_audit`, `streetview_survey`, `photo_match_evaluate`). When the same evidence (e.g. the residual audit's clusters) feeds a displayed build rather than being reported as a direct answer, the build follows the believability default above for whatever the evidence left unresolved.
- **AI Beautify light and outline** (user decision, 2026-10-23).
  - **Even light for 3D:** every station beautify (`buildStationBeautifyPrompt`: surveys, splat and texture bakes, swatches) is lit as under a bright overcast sky with no sun clause (`EVEN_LIGHT_SENTENCE`); `lighting: 'scene'` keeps the sun and mood only when the image is itself the final 2D picture. Renders and video that are the deliverable (`spatial_ai_render_scene`, keyframe video) build their own prompts and keep their light.
  - **Building-survey mode** (`survey_beautify_station` `mode: 'building-survey'`, opt-in): rendered from the tile photos, outline-locked in the prompt (`OUTLINE_LOCK_SENTENCE`) and checked by `checkStationOutline` in `BeautifyStationService`: overflow and underfill above the horizon under 3 % and the subject wholly in frame; and in every frame, aerials included (they have no sky to test): the image drawn, not the reference returned (`OUTLINE_MIN_CHANGE`), and no built structure where the reference is empty, neither the building drawn a second time nor invented neighbours (`OUTLINE_MAX_BUILT_OUTSIDE`); else the image is rejected and rerolled. Frame the station so the whole building fits, street to the top of its roof objects. Checks that read a station's edges (the planned survey-station roof check) use the standard image model at 1K (user decision, 2026-10-28: as sharp as 2K on the Plaza and cheaper; Nano Banana Lite makes no 2K image and returns the tile's soft edges); `survey_beautify_station` takes `imageModel` and `imageSize`.
  - **Character sheet** (`survey_beautify_station` `stationIds`, four stations; `building-character-sheet.ts`): the four views in one 2 x 2 sheet on white, one 4K Nano Banana 2 image with the registration framing lock (`CHARACTER_SHEET_FRAMING_LOCK`), split back into the station frames; every panel must pass the edge QC and `checkStationOutline`, else the whole sheet is regenerated.
- **Pipeline K is the 3D Building default** (user decision, 2026-10-26; supersedes pipeline J as the default for one building, from the chat and the 3D Building button alike; `pipeline-k/`, `parseStagedLocationArgs`). The real scan is kept and straightened, not rebuilt: tile_refine's walls flat on their fitted planes; each facade ortho's pier and storey lines traced (Viterbi, sub-pixel) and warped straight by a content-preserving mesh warp (line-collinearity and similarity terms; kept only when the lines get 20% straighter and the lattice is no less regular); smears levelled against the facade's own NCC-matched repeats (gain only); the photo's holes (texels it never reached) filled from the facade's own repeats, else the nearest real texel (labelled generated in the GLB extras); the facades rebuilt flat on those photos by the remesh polish (`facade-lattice.ts`, only cells the photo covers, read from the uncovered mask; a wall the wall grammar read from several overlapping facades is rebuilt once, as one sheet on its largest facade's plane, its photo the members' photos laid together and the rest filled from its repeats (generated), in place of them (`wall-sheets.ts`, `SCRATCHBOX_K_WHOLE_WALLS=0` off), and every facade also builds the cells its photo missed where the scan measures the wall inside its outline; tile_refine's photometric relief only analyses and exports the orthos for K, carving nothing in the scan (`reliefCarve: false`), and the lattice recesses each row's repeated windows as the straightened photo shows them, by the relief's own contrast rule (`PHOTO_RECESS`, photo-inferred), never shallower than the scan measures) and textured from tile_refine's twin, never re-baked; the twin's photos are de-lit only (no per-photo model recreate, which treated neighbouring photos differently and left patches; roofs seen from above, by a top-down height map per texel, get no shadow lift, since a dark roof is a dark material), then the cast shadow on every roof and terrace lifted by a sun fitted from the mesh itself (`roof-shadow.ts`, on by default (user decision, 2026-10-29), `SCRATCHBOX_K_ROOF_SHADOW=0` or the node graph's `twin.roofShadow` off: suns fitted per deck, per photo and per terrace, each gated on a clear lit/shadow step that no material change explains; the lift per channel in linear light, capped at the deck's lit level; photo-inferred; on the ESB 2,326 m² lifted, the harmonised seams unchanged, 39 s, but thin rims remain along the lifted areas' edges where the mesh's shadow edge sits a few decimetres off the photo's (its QA, `shadow-lift-qa.ts`: 11.2% of lifted texels halos, 32.7% lifted-lit, run 651b85ee); its top-down audit `roof_shadow_topdown.png` beside the twin, named in the run's `roof_shadow.json`), then harmonised (`texture-harmonize.ts`): one gain per photo toward a reference per side and height band, roof and wall apart, hidden up-facing shells left out, and seams levelled by a smooth per-photo offset field fitted where photos share a patch of surface, kept only when the seams get closer. **Base cleanup** (`base-cleanup.ts`, last in the polish): by the structure's footprint (Google's vector footprint, else the scan's outline): detached low pieces almost wholly outside it go; the building's triangles below 3 m outside it by 0.3 m go (low down, by any corner); the street itself (surfaces facing up within 0.6 m of the ground) goes everywhere, the scene's ground standing in; the base is closed with a generated skirt from the ground up to the lowest scanned surface along each edge's measured wall line, only where a wall stands near; then (user decision, 2026-10-28) every surface at any height is clipped exactly at the footprint plus 0.3 m (`clipToFootprint`, no jagged planes left standing out) and the openings are closed by the infill (`fillOpenLoops`, without the seal's cut and stitch; `SCRATCHBOX_K_CLIP=0` / `SCRATCHBOX_K_INFILL=0` off); no party wall is drawn (the base cleanup's wall spans and the image-model party wall texture are off, `SCRATCHBOX_K_PARTY_WALL_TEXTURE=1` on); and a footprint that does not fit the scan (more than 20% of the building above 3 m outside it) is not used at all, for the clip too. The tile seams are closed as the extraction arrives, before any stage reads it (`tile-seam-weld-service.ts` over the native `scratchbox_tile_seam_weld.hpp`: overlap trim, vertex weld, T-junction split, each within 3 cm, cached beside the extraction; `SCRATCHBOX_TILE_SEAMS=0` off), and every stage reads the welded scan; the raw extraction is kept. **No tears:** a scan triangle is removed only when every rebuilt facade it faces covers it, and a tear audit (each facade seen straight on, scan against result) puts the scan back over any torn pixel, else leaves that facade as scanned; the build reports what it found, restored and dropped, and leaves no torn pixel (a hole that remains was in the scan itself). **Material regions** (`material-regions.ts`, in the twin after harmonising; only with the app's texture library, `deps.pipelineK`; on again (user decision, 2026-10-30, with the facade reader reading the finished exterior; off 2026-10-28 to 10-30 because the openings' finishes were not calculated correctly), `SCRATCHBOX_K_MATERIAL_REGIONS=0` off): the photos stay the colour and the twin is drawn lit; the building's texels are split into CIELAB appearance classes, each matched to a non-metal library set by colour, finish and real tile size (a facade's scale: tiles of at most 8 m, ranked toward 2 m; the publisher's size, else a vision model's estimate from the set's preview, `texture-library-sizes.ts`, labelled generated in its sizeSource and scored against publisher sizes when made; any set of that scale not yet measured is measured first, best effort), then, when a vision model is available, the one among its 10 nearest that looks most like the class, shown beside the class's patches at the same real size and recoloured to its colour (`material-choice.ts`; the ranking's nearest when it picks none) (`material-sets.ts`; with `SCRATCHBOX_K_MATERIAL_PICK=spectrum`, by colour and texture measured at the tile's texel, `material-harvest.ts`), whose roughness and normal are drawn at its real size (generated). **Nothing is drawn metal** (user decision, 2026-10-28: a dark class is not a metal; no reading here tells one from dark stone). **Occlusion masks** (`pipeline-k/occlusion.ts`, on by default, `SCRATCHBOX_K_OCCLUSION=0` or the node graph's `remesh.occlusion` off): beside each facade ortho tile_refine writes how blocked the facade's clearest direction toward the capture was (per yaw of a fan of rays, the share of its elevations a surface blocks within 12 m, the least of those: a face between flanking walls seen straight on is clear, the buildings across a street are out of reach) (cast against the scan before the tree strip, else as loaded; measured geometry, no class of thing named), carried through the straightening warp; a texel at least 65% blocked is not read by the window fit, the wall grammar or the facade reader (greyed in its crops), so the lattice and the rhythm continue over it from the facade's repeats (generated, as over an uncovered span), a regular window column or row (or a strip) steps on into it at its own pitch from the clear side (`continueIntoOccluded`, generated: occluded spans lie mostly at a facade's edges, where the lattice completion, which needs windows on every side, never reaches), and a wall sheet takes the member that saw a texel clear; the facade is still rebuilt there with its photo. Openings come first from the **facade reader** (`pipeline-k/facade-reader.ts`, on whenever a vision model is available, `SCRATCHBOX_K_FACADE_READ=0` or the node graph's `remesh.facadeRead` off): a vision agent (`gemini-3.8-flash` at low thinking, the app's other vision models behind it; chosen 2026-10-29 for speed and cost) reads every plane of the building, the facade photos and every other plane photographed face on (`plane-orthos.ts`: roofs, terraces, slopes, the walls tile_refine did not analyse; walls at least 2 m wide and 10 m tall (a tower's narrow window-column faces included) before roofs and terraces, each kind the largest covered area first, up to 120, the rest reported unread): an overview splits the plane into zones, a full-resolution crop of each zone gives its openings (each window on its own), their pane splits and its glass (open-vocabulary words, and numbers: transparency, reflectivity, tint, opaque), the zone is tiled from that cell at the storey pitch measured over the zone (a narrow face, read after the wide walls, at their storey pitch when its rows skip storeys), only where the photo covers it (nothing generated), and the agent judges the outlines on the read crop and a held-out one, zone by zone; no brightness rule decides where a window is (on a tower each window is lit its own way). It reads the finished exterior (user decision, 2026-10-30; `pipeline-k/twin-reader.ts`): in the twin after the de-light, roof-shadow lift and harmonising, before the material regions, each facade from its own harmonised rebuilt texture (its straightened photo, same frame) and every other plane photographed from tile_refine's flat scan with its photos harmonised; it is first told the building (the request's name and address) and a brief of it, the largest planes on one contact sheet grouped into families by window system (`facade-reader-brief.ts`), every reading told the brief, its family and where its plane stands (the judge is told nothing), and a family's other planes look for its lead's accepted window in their own photo and tile that grid (`facade-reader-template.ts`, photo-inferred), read in full where it does not hold or falls under 60% of the lead's openings per covered square metre. Its readings draw the glass in place of the window fit's for the planes it drew; the window recesses, wall grammar and wall sheets stay the window fit's; a bay holding fitted panes takes glass on its panes alone, its spandrels the frame's finish. Elsewhere openings come only from the window fit (`window-fit.ts`, run on every facade plane whatever its photo's coverage, reading only covered texels; each accepted band's lattice completed from the facade's own repeats, `completeLattice`: a grid site flanked by windows is a window unless it looks more like the wall beside it, photo-inferred; a strip's panes read from its band's folded unit cell, split at the mullions, `panesOfUnitCell`): glass goes only in the bays the lattice's structure frames, on their texels that are not the wall's class, and on the fitted panes of punched windows outside the bays, less a pane most of whose texels are the wall's class (photo-inferred, the photo kept as the colour; each bay or pane carries a seed the viewer tilts it by, up to 1.5 degrees, generated); the window fit keeps a pane only where it reads unlike the stone beside its window, and a strip it cannot read gets none, the rest of each fitted window one frame finish (its most common darker class's set); the bays are read per wall, not per facade (`wall-grammar.ts`, after the window fit: coplanar facades that overlap or touch are one wall, its bays read from all their photos together, a span the photo never reached continuing the wall's rhythm, walls of one setback level a tier whose best-read wall lends its bays to an under-read one where its own photo is silent; generated where continued or borrowed); where the lattice draws bays, the **structure** (`facade-lattice.ts` `STRUCTURE`: the piers, bands and parapets the bays sit in) stands proud of the bays by the pier-to-bay depth of the scan before tile_refine flattened its walls, when it resolves one, else the photo's recess rule, else 0.10 m (generated), every structure edge chamfered 5 cm at 45 degrees, and only the structure takes the wall's (stone) set, the bays' infill the frame's, the photo staying the colour throughout; everywhere else the wall's set, whatever the colour. The viewer reflects the scene's probe on glass scaled by its weight (the probe holds no sun: a pane in shadow cannot mirror it; the sun's glint is the sun light's own shadowed highlight), the pane tilt kept until a pane shrinks under a pixel, its spread then handed to the roughness (floor 0.08), and the roughness rising where the normal varies within a pixel (`facadeMaterialLook.ts`), so distant glass does not shimmer. **Native kernels** (on by default; `SCRATCHBOX_K_NATIVE=0` runs the TypeScript, a comma list of `rectify`, `roof-shadow`, `regions`, `harmonize` only those; `pipeline-k/native/`): the straightening, the material regions' plan, the roof-shadow lift's loops (its roof cells, cell shadows and deck sums, and the lift) and harmonising's apply run as C++ ports, each held bit for bit to the TypeScript by its parity test; the last two run in one process a step on raw buffers (`twin_texels`, `scratchbox_twin_texels.hpp`), their threads capped by `SCRATCHBOX_K_NATIVE_THREADS`; a failed native build or run is thrown, never answered by the TypeScript path. ## 5. Real-world data and tiles

- **First-party services only:**
  - `GoogleMapsService` (geocoding: Google Places API (New) Text Search, no place dictionaries);
  - `Google3DTileService`, `GoogleElevationService`, `LocalTangentPlane` (WGS-84 ↔ ENU).

  The generic `google_maps_platform` plugin skill is deactivated; never load it or fetch its index.
- **Tile ingestion quality:**
  - stream to the deepest leaf LOD (`errorTarget ≤ 0.5`, 4K screen-space error) and wait for streaming to settle;
  - write binary `.glb` and keep the raw extraction;
  - start new workflows from a fresh extraction, never from stale intermediate `.glb`s in `public/models/`;
  - no landmark dictionaries or coordinate hashes: missing coordinates or credentials throw an actionable error.
- **Atomic building integrity.** No extraction boundary, slice or frustum may cut through a building. The vertical extent is unbounded upward. Grow the boundary to whole connected structures and natural clearings. Contextual cameras must cover the full skyline height.
- **Camera dataset conventions** (Nerfstudio export):
  - OpenCV → Nerfstudio camera-to-world flips the Y and Z columns: T_ns = T_cv · diag(1, −1, −1, 1);
  - masks are binarized at ≥ 128;
  - moving subjects are initialised by visual-hull carving (`NerfstudioDatasetService.carveVisualHull`), not COLMAP;
  - dense splatfacto training is not run by the app: export the dataset instead.

## 6. Engineering practice

1. **Investigate before editing.** Read the files, never guess symbol names or paths. Keep TypeScript typechecks clean across all packages (`npm run typecheck`).
2. **Mechanical reality, no simulation traps** (`.agents/skills/prevent-architectural-simulation-trap/SKILL.md`):
   - no hollow interfaces or factories without two real implementations;
   - no stubs (`return null;`, `// TODO`);
   - no mock-only tests: assert transformed data, counts, magic bytes;
   - never claim a build or test passed without running it and seeing exit code 0.
3. **Tests never bill.** Run vitest with credentials unreachable (empty HOME, credential env vars unset). Real-model runs happen outside tests, on purpose.
4. **Screenshots as evidence.** UI, canvas and 3D work is checked by looking at the rendered result, with screenshots at milestones. Test screenshots go to `test-results/screenshots/` or `docs/screenshots/` (gitignored). Rendered pixels, not passing checklists, decide quality; use the `visual-critic` skill for judgments. A neutral studio void is correct when nothing asked for an environment (§3.6).
5. **Live verification in the app.** Use the `operate-scratchbox` skill:
   - add your own `scratchbox-<branch>` launch entry on free ports;
   - never touch the user's `scratchbox-dev` entry (ports 3060-3062) or `.claude/worktrees/latest-main`;
   - record findings in `docs/processes/` with a README row.
6. **Commits.**
   - **Shape:** small logical commits, staging only the files your task touched (never `git add -A`); the working tree often holds other sessions' work.
   - **Pushing:** fast-forward only, never force-push.
   - **Before deleting:** look at a file or folder, and check for references (links in `desktop-app/public`, the hydration list in `manifests/demos_asset_manifest.json`), before removing it.
7. **No leaked plumbing.**
   - **User code:** never paste engine internals (solar trigonometry, tile octree walkers, clippers, distortion matrices, shaper source) into user code or chat.
   - **Sandboxes:** live-code sandboxes import from `@scratchbox/core`.
   - **Chat:** report tool use as concise status, not implementation.
